# Второй мозг проекта — работа с Notion

Хаб: https://app.notion.com/p/3b4d8ed2625581289c6bec51f3361365

Структура: хаб (статус, P0, задачи, быстрый старт) + три подстраницы —
«Архитектура и карта репозитория», «Сверка с продакшеном», «Журнал решений».

## Правило цикла — оно главнее всего остального в этом файле

**Цикл** — от начала сессии (или от последнего `git push`) до следующего пуша.

- Репозиторий разбирается **один раз за цикл**, и только если Notion не ответил.
- Итог разбора **сразу** уходит в Notion.
- Дальше до конца цикла — **исключительно Notion**, обратно в код не лезем.
- Новый цикл открывает `git push`.

Исключения — только четыре, и каждое означает чтение **одного адресного файла**,
а не новый общий разбор: правлю именно этот файл; в Notion тут стоит
«не проверено»; Notion противоречит наблюдаемому поведению; пользователь прямо
попросил посмотреть код. После любого из них — записать результат в Notion,
чтобы второй раз читать не пришлось.

Полная формулировка правила — в `CLAUDE.md` в корне репозитория.

## Чтение — от дешёвого к дорогому

Идти строго по порядку, останавливаться как только ответ найден.

1. **Поиск по дереву.** `notion-search` с `page_url` хаба — он покрывает и
   подстраницы. Ставить `page_size: 3–5` и `max_highlight_length: 200`.
   Это десятки строк. В большинстве случаев достаточно.
2. **Fetch нужной подстраницы.** Если поиск дал направление, но не детали —
   забрать одну подстраницу, а не хаб целиком.
3. **Fetch хаба.** Только когда нужен общий статус или список P0.

Не запускать заново проверки, результаты которых уже лежат в «Сверке
с продакшеном». Там сырые коды ответов и заголовки с датой.

## Запись — обязательный шаг, если что-то выяснилось

Второй мозг ценен ровно настолько, насколько он свежий, и правило «один разбор
за цикл» держится только на записи. Не записал — следующая сессия начнёт с нуля.

Куда что:

| Что выяснилось | Куда |
|---|---|
| Новая поломка или риск | P0 в хабе |
| Изменился статус области | «Светофор» + цифры в дашборде |
| Проверено что-то на проде | «Сверка с продакшеном» + дата |
| Принято архитектурное решение | «Журнал решений» |
| Изменилось назначение файла | «Архитектура и карта репозитория» |
| Задача по коду | `TODO.md` в репозитории, **не** в Notion |

Как править:

- Только `update_content` с точечными `old_str` / `new_str`. Никогда
  `replace_content` — снесёт подстраницы.
- `allow_deleting_content` не выставлять. Значение по умолчанию защищает
  подстраницы: при риске удаления операция упадёт, а не молча сотрёт.
- Перед правкой перечитать целевую страницу — `old_str` должен совпадать
  побайтово. Notion переписывает язык код-блоков (`text` → `plain text`),
  так что фенсы сверять по факту, а не по памяти.
- Опровергнутое не удалять молча, а помечать поправкой в «Журнале решений»
  с датой. Иначе через месяц никто не поймёт, почему запись изменилась.

## Правила достоверности

- Разделять **проверено** и **не проверено**. Если проверки не было —
  писать «не установлено», а не догадку.
- Числа в дашборде должны быть посчитаны, а не оценены на глаз.
- `TODO.md` — источник истины по коду; Notion — по проду и решениям.
  Расходятся: верить коду, править Notion.
- Не отправлять POST на `/api/lead` продакшена — создаст реальную заявку
  и сообщение в Telegram.
